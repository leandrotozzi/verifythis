## The reference model in C

#### *The scoreboard that rewrites the spec*

- The scoreboard of the course predicts **in SystemVerilog**: a `case` with the
  arithmetic of the VTALU. For five eight-bit operations it is perfect
- For a DSP, a codec or a crypto engine, that arithmetic **already exists, and in C**:
  the algorithm team wrote it, and it is against that model that the spec was signed off
- Rewriting it in SystemVerilog is maintaining **two** models and spending the project
  debugging the difference between them. That is not verifying: it is having two specs
- The way out is not to rewrite it. Verilator compiles to C++, so the model gets
  **linked inside the simulation**: no socket, no separate process, no IPC

Note:
This is the technique that separates a course testbench from a production one, and the
argument is not about convenience: it is about **authority**. In a project with serious
arithmetic, the spec is not a PDF — it is a program in C that somebody ran against a thousand
vectors before the RTL existed. A scoreboard that reimplements that
program in SystemVerilog does not verify the DUT against the spec: it verifies the DUT
against the reading the verifier made of the spec, which is another thing.
The question worth throwing at the group before showing the code: *"if the
C model and the scoreboard differ, who is right?"*. The uncomfortable answer
is that you do not know, and finding out costs days. With DPI the question does not
exist because there is only one model.
And the reason why this section is so cheap in this course: DPI is part of the LRM
and the commercial simulators ship it as a base feature —what leaves it out are the
free student editions—; what costs you in a commercial flow is the *toolchain*:
`-sv_lib`, compiling the `.c` separately, and remembering the library on every run.
Here the simulator compiles to C++ by design, so the bridge is one more file on the
command line and there is nothing to configure.

## The reference model in C

#### *`import "DPI-C"`: one declaration on each side*

{{code:code/u8/dpi/vtalu_pkg.sv#the-imports}}

{{code:code/u8/dpi/vtalu_golden.c#the-golden}}

- The name after `"DPI-C"` is **the symbol the linker looks for**: it has to
  match letter by letter with the one in the `.c`
- An `input int` travels as an `int`; an `output int` arrives as an `int *`. A
  `function` cannot consume time; a DPI `task` can, but only declared `context` and
  calling back into an `export "DPI-C" task`
- The `.c` goes on the `verilator` line as one more source. **There is no DPI flag**

Note:
It is worth reading the two declarations side by side, because the symmetry is the whole
mechanism: the one above is the promise and the one below is who keeps it, and the
compiler does not cross-check them — the one who joins them is the linker, at the end. Out of that comes the
number one failure mode of DPI, which is worth naming before it shows up: an
*undefined reference* to a function that is written, right there, in plain sight. Almost
always it is one of two things — the name does not match, or the file got compiled as
C++ and the symbol came out with a mangled name.
That last one is literally what happens here: Verilator hands the user's sources
to the C++ compiler, so the `.c` needs the `extern "C"` that is
in the file. Without that guard, the example does not link and the error does not say why.
The type table of the LRM is longer —there is `svBitVecVal` for wide vectors,
`svOpenArrayHandle` for arrays— and it is not needed here. The rule of thumb: if the
data fits in an `int`, the signature writes itself; if not, you look up annex H of the
1800 and copy it.

## The reference model in C

#### *The scoreboard: the prediction gets asked for, not written*

{{code:code/u8/dpi/tb_classes/scoreboard.svh#predict_result}}

- It is **the only** difference from the scoreboard of the sequences. The monitor, the
  analysis port, the FIFO, the `do_compare` and the `uvm_error` do not change
- The golden model replaces the six lines of predicting, and no other piece
  of the testbench finds out there is C on the other side
- And the border gets crossed in both directions: `vtalu_golden_bug(1)` is
  SystemVerilog **changing the state** of the C model

Note:
The count is worth doing out loud because it is the design argument of the whole
unit: one six-line function changed and nothing else did. That happens because
the scoreboard was already well divided up —predicting and comparing are two jobs, and
they were in two methods—, and it is the late reward for having separated
`predict_result` from `write` three days ago.
The `int'(...)` line is the one to point at: the UVM types do not cross the
border. On the other side there is no `command_transaction`, there are three integers. When the
data is an object —an image, a packet, a matrix— what gets passed is a
pointer or an open array, and the one who decides the format is the C model, not the
testbench.
And the `vtalu_golden_bug` is not an ornament: **a scoreboard that has never seen an error
is not tested**. `run.sh` runs the same test against a mutated model —the
multiplication truncated to eight bits— and demands that the scoreboard scream. If it does not
scream, the testbench is comparing against itself and nobody was going to find out. It is
the same mutation test the checker of the capstone does with `+BUG=1`, from the
other side of the wire.

## The reference model in C

#### *What you gain, what you pay*

| You gain | You pay |
| --- | --- |
| **One single model**, the one that signed off the spec | the opcodes get synchronized **by hand**: one `enum` on each side |
| The model gets tested with the tools of C | an `undefined reference` does not say which of the two declarations is wrong |
| Arithmetic that in SystemVerilog is painful —floating point, matrices, crypto— | the C model runs in **zero time**: it cannot wait for an edge |
| Performance: it is a function call, not an IPC | a `segfault` in the model takes the whole simulation down with it |

- The rule for deciding: if the prediction **already exists in C**, DPI. If you write it
  yourself from scratch and it is five lines, a `case` in SystemVerilog and that is it
- It runs: `make u8/dpi` — two tests against the healthy model, and one against the mutated one

Note:
The table is what has to be left written down, and the row that gives the most discussion is the
first one on the right: the duplicated `enum`. It is real and it has no elegant solution
—the LRM does not share types between the two sides—, and it is the first thing to
look at when **all** the comparisons fail at once. If one in every
six fails, it is the DUT; if all of them fail, it is the mapping.
The third row on the right is the one that surprises and is worth getting ahead of: a DPI
`function` runs in zero time, so the C model cannot synchronize with the clock. That
is what `import "DPI-C" task` is for — with one clarification almost every tutorial
skips: C cannot block by itself. A DPI task consumes time **only** if it is declared
`context` and the C calls back into an `export "DPI-C" task` of SystemVerilog, which
is the one that waits for the edge. And there it is no longer a golden model, it is a
bus model, which is another topic.
The rule of the second-to-last bullet is the one to take away, because the risk of
this section is that somebody comes out wanting to do everything through DPI. The VTALU does **not**
justify DPI: five eight-bit operations get written in a `case` and read
better. The example exists so the technique has been seen when the DUT that does
justify it comes along, and that DUT arrives sooner than you think.
