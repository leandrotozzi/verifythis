Agenda

Day 8 · ≈ 4 h · optional · what comes after the capstone

  • RAL, unit 9 — the register model over the same APB
  • The reference model in C, through DPI
  • The second capstone: a FIFO with backpressure

This day is optional and it goes after the wrap-up, and both things are on purpose. The course ends on day 7: whoever got that far wrote a complete UVM testbench from a blank sheet and lacks nothing to work. What is here is what gets added once that has happened. Why these three and not others: all three need the capstone to be already done. RAL replaces the scoreboard the student has just written —and it is not understood before having written it—; the golden model in C replaces the prediction of the scoreboard, the same thing; and the second capstone only makes sense for whoever has already handed in the first one, because what it teaches is where the pattern of the first one stops being any use. For whoever is teaching: in a company this is another half day, and it usually gets given when the group has real registers in the project. In a semester it is the optional unit, or the final project for those who want a high mark.

RAL

Unit 9 · optional · the register stops being an address

  • Every chip has configuration registers, and a small SoC has two hundred
  • Without RAL, the testbench writes them like this: addr = 8'h04, wdata = ..., and the scoreboard keeps a logic [31:0] for each one
  • The day the architect moves SCRATCH from 0x04 to 0x24, you have to look for 8'h04 all over the testbench — and 0x04 was also the value of something else
  • RAL —Register Abstraction Layer— is the layer that puts a name on that: model.SCRATCH.write(status, 'h1000_0000)
  • It is optional and it goes at the end on purpose: it is only understood once you have written the testbench it replaces

This unit is short and it is the last one, and both things are deliberate. RAL is the piece of UVM most often taught without context —there are courses that give it on day 2— and that way it is not understood: it looks like one more API. With the capstone just done, on the other hand, the student has the comparison inside their head. They wrote the scoreboard that predicts CTRL; now I show them the library that does it on its own, and also where it does not. The number of 200 registers is not rhetorical. A PHY block or a memory controller has that many, and the register spec arrives as a spreadsheet. The next step, which this course does not take, is generating the model from that spreadsheet with IP-XACT or SystemRDL: nobody writes 200 registers by hand. It is worth saying, because otherwise the student walks away with the idea that RAL is a lot of typing. And the argument about moving 0x04 to 0x24 is the one that convinces a sceptic: it is not elegance, it is that the map gets written only once.

RAL

Three pieces, and only one knows what bus is underneath

Piece What it is How many times it gets written
uvm_reg_block the map: registers, fields, addresses one per DUT
uvm_reg_adapter translates access ↔ bus transaction one per protocol
uvm_reg_predictor what the monitor saw, said in registers none: it comes done
  • The model does not know there is an APB underneath. You change the adapter and the same model drives AHB
  • The adapter is the file that comes with a VIP you bought. It is twenty lines
  • And underneath everything, without a single change: the driver, the monitor and the agent of the capstone

The table is the slide. That the third column says one per DUT, one per protocol and none is the whole economic argument for RAL, and it is the one that holds the decision up in a project meeting. It is worth pointing at the last line with a finger: nothing the student wrote yesterday gets replaced here. code/u9/ral/ compiles the interface, the transaction, the driver, the monitor and the agent of d7-final/solucion/ exactly as they are, through +incdir. RAL is a layer, not a different testbench — and it is the reason why this unit fits into three files. If somebody asks about the backdoor: it exists, it gets declared with add_hdl_path and it reads the signal of the RTL without going through the bus. It does not go into the course because it depends on the hierarchy support of the simulator, which is precisely what changes between tools. The frontdoor —the one that uses the real bus— is the one you have to know.

RAL

The model: the table of the spec, in code

  • A field gets declared with configure(), and the argument that matters is the access string: "RW", "RO", "WOC"…
  • That string is the specification. It is not documentation: it is what UVM uses to predict, and to generate the tests of the last slide

configure(parent, size, lsb_pos, access, volatile, reset, has_reset, is_rand, individually_accessible) — nine positional arguments, and it is the ugliest signature in UVM. It is worth writing it on the blackboard once; afterwards the student copies it from the example, which is what everybody does. CLR is the field that justifies the slide. The spec of the capstone says "writing a 1 puts ACC and OVF at zero, and the bit always reads 0", and that is trap 2 of the small print — the one that makes the hand-written scoreboard fail. UVM has an access that says exactly that and it is called WOC: on the write the mirror goes down to zero, and the read side of the field is not used to predict anything. The complete list of accesses is in the LRM 1800.2, and there are twenty-five. You do not have to know them by heart: you have to know that the list exists, and look there before inventing a set_compare or a callback. Half of the bad register models you come across are an RW field with patches on top.

RAL

The adapter: the only thing that knows there is an APB

  • reg2bus goes down: the model asks for a generic access, this builds the transaction of the bus
  • bus2reg goes up: the transaction comes back —from the driver, or from the monitor— and this counts it in terms of an access
  • PSLVERR turns into UVM_NOT_OK, and there the status of every write() stops being decorative

Twenty-two lines, and that is the whole file. It is worth saying the number out loud, because RAL has a reputation for being heavy and the project-specific part is this one. The reg2bus / bus2reg symmetry is the one to fix: one function per direction, and neither of the two has state. The uvm_reg_bus_op is the common currency —kind, addr, data, status— and it is deliberately as flat as possible: any register bus fits in there. The const ref of the reg2bus comes from the signature of the base class and has to be copied exactly. It works on Verilator 5.052, which was not obvious. And a warning from the field: bus2reg is called by the predictor too, with the item the monitor saw. An adapter that reads something from the driver —or that depends on having built the transaction itself— works with automatic prediction and breaks the day you switch to explicit. That is why both functions are pure.

RAL

Hooking it up: three lines and a connect_phase

  • set_sequencer is what makes model.CTRL.write() end up in the driver: the model sends items through the sequencer of the agent that already existed
  • set_auto_predict(0) switches off the automatic prediction, and the uvm_reg_predictor replaces it by listening to the analysis port of the monitor
  • And the model.build() of the build_phase: a uvm_reg_block is a uvm_object, not a component. Nobody calls it for you

The phase trap that takes everybody's first afternoon is the last line of the slide. apb_reg_block::type_id::create("model") gives back an object with zero registers, because build() here is an ordinary method that gets called by hand —not the build_phase of a component, which UVM walks on its own—. The symptom is a uvm_fatal from uvm_reg_map that talks about a null register and does not mention the word build. The second thing to point out is where the sequencer comes from: it is agent_h.sequencer_h, the same one from the capstone, the same one the normal sequences run on. RAL does not bring a sequencer of its own. That means a register sequence and a traffic one compete for the same driver, and there the priorities show up — which is a topic for another course, but it is worth them knowing it exists.

RAL

Prediction: who tells the model what happened

Who predicts What happens if the DUT does something else
automatic the write() call itself the model does not find out: it believes what it meant to send
explicit the uvm_reg_predictor, from the monitor the model believes what happened on the wire
  • The automatic one is one line fewer and it is the one that comes up in the tutorials
  • The explicit one is the one to use, and for the same reason the scoreboard of the capstone looks at the monitor and not at the driver
  • And it is free: the monitor and its analysis port were already there

This is the judgement slide of the unit and it is worth not rushing it. With set_auto_predict(1), model.CTRL.write(status, 'h1) updates the mirror at the moment it gets called, before the bus has done anything. If the driver sends the transfer wrong, or the DUT ignores it, the model goes on being convinced that EN=1. It is exactly the design mistake the course has been attacking since day 1: the one who checks cannot believe the one who drives. With explicit prediction the path is the long and correct one: the driver drives, the monitor sees the wire, the analysis port publishes it, the predictor calls bus2reg and only then does the mirror change. It is the same drawing as the scoreboard, with a piece of the library instead of a hand-written class. The bonus, which can be seen in the example: since the predictor listens to the bus and not to the calls, the model also finds out about the transfers somebody else made — another sequence, another master, an ordinary module. Automatic prediction cannot do that even in principle.

RAL

The stimulus, without a single PADDR

  • There is no address in any call: the address is in the map
  • Nobody assigned the mirror. get_mirrored_value() gives back 1 because the monitor saw the transfer and the predictor counted it
  • Underneath, the driver of the capstone is doing SETUP, ACCESS and the wait state of the read, the same as yesterday

bash run.sh · code/u9/ral/

It is worth running it live and looking at the log with grep MONITOR: for every line of stimulus there is a complete APB transfer, with its address and its handshake, done by the driver they wrote. It is the demonstration that RAL does not replace the testbench, it drives it. The line most worth discussing is model.CTRL.read(status, data) against model.CTRL.mirror(status, UVM_CHECK). Both read from the DUT. The difference is that mirror compares against what the model believed before the read, and if it does not match it reports a uvm_error without anybody writing a check. It is a register scoreboard in one word. And the third form, which is not on the slide and is worth naming: set() + update(). set() changes the desired value in the model, without touching the bus, and update() writes only the registers whose desired value differs from the mirror. It is how a whole block gets configured at the start of a test, and it is where RAL stops being convenient and starts genuinely saving simulation time.

RAL

The tests you did not write

  • Both come from uvm-core. They know nothing about this DUT: they read the model and generate the stimulus and the check out of it
  • uvm_reg_hw_reset_seq reads everything after the reset and compares it with the reset value declared
  • uvm_reg_bit_bash_seq writes and reads every writable bit of every register, one by one, in both directions

This pair of sequences is the RAL argument that wins discussions, because it does not appeal to taste: they are two real tests, free, that on a block of 200 registers cover 80 % of the bugs of address decoding and of fields wired the wrong way round. There are more in the library and it is worth naming them: uvm_reg_access_seq (writes through the frontdoor and reads through the backdoor, and the other way round), uvm_reg_shared_access_seq for registers in more than one map, and uvm_mem_walk_seq for memories. The ones that need a backdoor stay out of the course for what was said before. The implementation detail worth telling, because it explains why the model has to be right: bit_bash skips the read-only fields and the ones that are not individually accessible, and it uses the access string to know what to expect back. Which means the quality of the test they give you is exactly the quality of the model you wrote.

RAL

And that is why the model is the spec

    CTRL.CLR as "WOC"  0 UVM_ERROR
    CTRL.CLR as "RW"   2 UVM_ERROR, from uvm_reg_bit_bash_seq
    > Writing a 1 in bit #1 of register "model.CTRL" ... yielded 'h0
      instead of 'h2
  • One word changed in a string, and a sequence nobody wrote catches it with the number of the bit
  • It is trap 2 of the small print of the capstone —CLR never reads as 1— and there a whole scoreboard was needed to see it
  • The register model is the only document of a project that is the spec and the code at the same time

bash run.sh runs both versions and compares them

This is the slide that justifies the unit, and the run.sh of the example produces it on its own: it runs builtin_test with the model right and with +MAL, which declares CLR as RW, and shows the two numbers side by side. The punchline to say out loud: in the capstone, that same trap cost writing a scoreboard, modelling the autoclear by hand and discovering the bug with a message of your own. Here it costs picking one word well, and the error message is written by Accellera, with the number of the bit inside. The honest downside, which has to be said so it does not sound like a brochure: if you get it wrong the other way round —you declare RW a field the DUT implemented as RW when the spec said something else— the model and the DUT agree on the mistake and no sequence says anything. The register model verifies the DUT against the spec written in the model, not against the real spec. That is why the review of the model against the document is still human work, and that is why stage 1 of the exercise prints the map so it can be compared by hand.

RAL

What RAL does not do, and it has to be said

  • ACC and STATUS have an address, but they are not registers: their value gets produced by a write to another address
  • A model predicts "what I wrote is what I am going to read", and for these two that sentence is false. set_compare(UVM_NO_CHECK) says so in the model
  • The accumulator goes on being checked where it already was: in the scoreboard, which is the one that knows how to add
  • The read updates the mirror all the same — a read is a prediction

If they take a single idea away from this unit, let it be this one: an address is not a register. RAL models addressable storage, and it does it very well. It does not model behaviour. The accumulator of the capstone —which adds only with EN=1, which overflows, which gets cleared with CLR— is behaviour, and that lives in the scoreboard, as it lived yesterday. The failure mode of not saying it is the worst of all and it is an everyday one: the team puts RAL in, switches on mirror(UVM_CHECK) over the whole map, and the regression fills up with errors on the status registers. Since they are false positives, somebody switches the check off entirely — and from then on the model verifies nothing and nobody finds out. The difference between switching off three named fields and switching off the global check is the whole difference. The two UVM_WARNING the example prints —GET_MIRRORED_VAL/VOL— are the library saying the same thing on its own account: the mirror of a volatile field is not evidence. They are in the output on purpose.

RAL

Summary of the unit

  • The model is the map of the spec in code, and the access string of each field is the part that verifies
  • The adapter is the only thing that knows about the bus: twenty lines, once per protocol
  • The prediction goes through the monitor, not through the call — the same rule as the scoreboard
  • It gives you hw_reset_seq and bit_bash_seq for free, and it charges you knowing what is not a register
  • And all of this runs on Verilator 5.052, which until today nobody had shown

The close of the unit and of the technical course. The last line is not marketing: when writing this unit it was first tested whether uvm_reg_adapter and the frontdoor worked on Verilator, before writing a single slide, and the result is measured in docs/verilator.md. Everything the unit uses works: the model, the adapter, the uvm_reg_predictor, mirror(UVM_CHECK) and the two sequences of the library. For whoever goes on alone, the order of what is missing: uvm_reg_access_seq with a backdoor, generating the model from IP-XACT or SystemRDL —which is how it is really done—, and uvm_mem for memories. All three are extensions of what they saw here, not new topics. And the bridge to the exercise: the first thing they are going to be asked for in a project with registers is exactly this, with the spreadsheet of the spec on the left-hand side of the screen.

Exercise · Day 8

Modelling the register map

cd code/ejercicios/d8-ral && cat README.en.md

  • It is literally the first thing you get asked for in a project with registers: they give you the table of the spec and you give back the model
  • The DUT and the testbench are the ones from the capstone. The adapter, the predictor and the tests come from the unit. The only thing you write is apb_reg_block.svh
  • Four registers, six fields, forty lines
  • The checker goes in stages: the map —printed and compared with the table, without simulating anything—, the accesses —the two sequences of the library— and what the model cannot predict

It is the shortest exercise of the fifteen and the one most like a real task from the first weeks of a project. Forty lines, and half of them are copying and pasting the pattern of CTRL. The stage that teaches is stage 1, and for a reason of method: the model gets printed —+UVM_TESTNAME=mapa_test— and gets compared line by line against the table of spec.en.md, before simulating anything. It is what has to be done with a real register model, where the typical mistake is not about UVM but an offset copied wrong from a 200-row spreadsheet. Stage 2 is where CLR falls: whoever declared it RW passes stage 1 without a problem and finds out here, with the number of the bit, thanks to a test they did not write. It is worth letting them fall there — it is the moment when the RAL argument stops being an opinion. And stage 3 is the one that separates: it asks you to switch off a check, which is the opposite of what the course has been asking for the last seven days. The justification has to come from them: STATUS.EN changed because of a write to another address, the model cannot know it, and a false positive that gets let through ends up with somebody switching the whole check off.

The reference model in C

The scoreboard that rewrites the spec

  • The scoreboard of the course predicts in SystemVerilog: a case with the arithmetic of the VTALU. For five eight-bit operations it is perfect
  • For a DSP, a codec or a crypto engine, that arithmetic already exists, and in C: the algorithm team wrote it, and it is against that model that the spec was signed off
  • Rewriting it in SystemVerilog is maintaining two models and spending the project debugging the difference between them. That is not verifying: it is having two specs
  • The way out is not to rewrite it. Verilator compiles to C++, so the model gets linked inside the simulation: no socket, no separate process, no IPC

This is the technique that separates a course testbench from a production one, and the argument is not about convenience: it is about authority. In a project with serious arithmetic, the spec is not a PDF — it is a program in C that somebody ran against a thousand vectors before the RTL existed. A scoreboard that reimplements that program in SystemVerilog does not verify the DUT against the spec: it verifies the DUT against the reading the verifier made of the spec, which is another thing. The question worth throwing at the group before showing the code: "if the C model and the scoreboard differ, who is right?". The uncomfortable answer is that you do not know, and finding out costs days. With DPI the question does not exist because there is only one model. And the reason why this section can exist in this course and not in another: DPI is part of the LRM, but getting to use it in a commercial flow asks for the licence that enables it. Here the simulator compiles to C++ by design, so the bridge is one more file on the command line.

The reference model in C

import "DPI-C": one declaration on each side

  • The name after "DPI-C" is the symbol the linker looks for: it has to match letter by letter with the one in the .c
  • An input int travels as an int; an output int arrives as an int *. A function cannot consume time; a DPI task can
  • The .c goes on the verilator line as one more source. There is no DPI flag

It is worth reading the two declarations side by side, because the symmetry is the whole mechanism: the one above is the promise and the one below is who keeps it, and the compiler does not cross-check them — the one who joins them is the linker, at the end. Out of that comes the number one failure mode of DPI, which is worth naming before it shows up: an undefined reference to a function that is written, right there, in plain sight. Almost always it is one of two things — the name does not match, or the file got compiled as C++ and the symbol came out with a mangled name. That last one is literally what happens here: Verilator hands the user's sources to the C++ compiler, so the .c needs the extern "C" that is in the file. Without that guard, the example does not link and the error does not say why. The type table of the LRM is longer —there is svBitVecVal for wide vectors, svOpenArrayHandle for arrays— and it is not needed here. The rule of thumb: if the data fits in an int, the signature writes itself; if not, you look up annex H of the 1800 and copy it.

The reference model in C

The scoreboard: the prediction gets asked for, not written

  • It is the only difference from the scoreboard of the sequences. The monitor, the analysis port, the FIFO, the do_compare and the uvm_error do not change
  • The golden model replaces the six lines of predicting, and no other piece of the testbench finds out there is C on the other side
  • And the border gets crossed in both directions: vtalu_golden_bug(1) is SystemVerilog changing the state of the C model

The count is worth doing out loud because it is the design argument of the whole unit: one six-line function changed and nothing else did. That happens because the scoreboard was already well divided up —predicting and comparing are two jobs, and they were in two methods—, and it is the late reward for having separated predict_result from write three days ago. The int'(...) line is the one to point at: the UVM types do not cross the border. On the other side there is no command_transaction, there are three integers. When the data is an object —an image, a packet, a matrix— what gets passed is a pointer or an open array, and the one who decides the format is the C model, not the testbench. And the vtalu_golden_bug is not an ornament: a scoreboard that has never seen an error is not tested. run.sh runs the same test against a mutated model —the multiplication truncated to eight bits— and demands that the scoreboard scream. If it does not scream, the testbench is comparing against itself and nobody was going to find out. It is the same mutation test the checker of the capstone does with +BUG=1, from the other side of the wire.

The reference model in C

What you gain, what you pay

You gain You pay
One single model, the one that signed off the spec the opcodes get synchronized by hand: one enum on each side
The model gets tested with the tools of C an undefined reference does not say which of the two declarations is wrong
Arithmetic that in SystemVerilog is painful —floating point, matrices, crypto— the C model runs in zero time: it cannot wait for an edge
Performance: it is a function call, not an IPC a segfault in the model takes the whole simulation down with it
  • The rule for deciding: if the prediction already exists in C, DPI. If you write it yourself from scratch and it is five lines, a case in SystemVerilog and that is it
  • It runs: make u8/dpi — two tests against the healthy model, and one against the mutated one

The table is what has to be left written down, and the row that gives the most discussion is the first one on the right: the duplicated enum. It is real and it has no elegant solution —the LRM does not share types between the two sides—, and it is the first thing to look at when all the comparisons fail at once. If one in every six fails, it is the DUT; if all of them fail, it is the mapping. The third row on the right is the one that surprises and is worth getting ahead of: a DPI function runs in zero time, so the C model cannot synchronize with the clock. That is what import "DPI-C" task is for, which can consume time — and there it is no longer a golden model, it is a bus model, which is another topic. The rule of the second-to-last bullet is the one to take away, because the risk of this section is that somebody comes out wanting to do everything through DPI. The VTALU does not justify DPI: five eight-bit operations get written in a case and read better. The example exists so the technique has been seen when the DUT that does justify it comes along, and that DUT arrives sooner than you think.

Capstone 2 · Day 8

The second final: a FIFO with backpressure

cd code/ejercicios/d8-fifo && cat spec.en.md

  • For whoever has already handed in the APB. The protocol is simpler —there are no addresses, no wait states, no error response— and even so it is harder
  • The APB one is a slave with no useful memory: an address and a value, and the scoreboard can be a table of four rows. A FIFO has order and occupancy, and both have to be carried
  • The bug of +BUG=1 is not a data bug: almost_full goes up one place late. The data still comes out right and in order, so a scoreboard that only compares rd_data passes green
  • The small print: the flags describe the state before the edge, rd_data arrives one cycle late, writing with the FIFO full is not an error, and a simultaneous read makes room for the write

This is the exercise that separates whoever understood from whoever copied the pattern, and the mechanism by which it separates is in the third bullet: the bug is in a control output, not in the data path. A scoreboard that compares what comes out of rd_data closes six of the seven rows of the plan and passes green with the DUT broken. To see it the flags have to be predicted, and to predict the flags the occupancy has to be modelled — that is, writing a reference model with state, which is what the first capstone could not ask for. It is worth saying why it goes second and not first: the APB is the DUT you run into in the first year, and the table-address-value pattern is the right one there. This one teaches when that pattern stops being any use, and that lesson is not understood without having used the pattern before. The trap that catches the most people is the order of updating the model: first look at whether the read takes something out —that frees a place— and only then whether the write goes in. The other way round, the simultaneous write with the FIFO full shows up as a lost piece of data that the DUT never lost, and the student spends an hour looking for the bug in the RTL. And the second one: the check_phase that claims data that never came out. Almost always the test ended one cycle too early, and it is the drain_time of day 3 showing up where nobody expected it.
