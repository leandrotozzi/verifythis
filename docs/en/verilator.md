# The Verilator matrix

Generated by `sh tools/verilator-matrix.sh` (or `make matrix`). **This
expires**: it holds for the version and the date below, not in general.

- **Verilator**: `Verilator 5.052 2026-09-05 rev v5.052`
- **UVM**: 2020.3.1 (Accellera uvm-core, IEEE 1800.2-2020) — `make uvm`
- **Date**: 2026-09-08
- **Result**: 38 pass, 0 fail

Verilator is the only simulator of the course. There is no Questa flow: the
`run.do` files were deleted and so was the VHDL DUT.

```sh
make              # the 38 examples
make u4/tests         # a single one
make matrix       # all of them, and regenerates this file
```

The examples with UVM take **minutes** to compile (100-121 s each in CI, 15 s with
a warm ccache). The full run is
almost an hour. The shared flags live in `code/verilator/common.sh`.

## Requirements: Verilator alone is not enough

| | What for | If it is missing |
|---|---|---|
| `z3` | `randomize()` with constraints: Verilator calls an external SMT solver | it compiles, it runs, and **`randomize()` returns 0**. It affects `u5/varios-objetos`, `u6/transactions`, `u7/agents`, `u7/sequences` and the exercises of days 5, 6 and 7 |
| `ccache` | optional: it brings the second compilation of a UVM example down from 92 s to 15 s | nothing, it recompiles the whole thing every time |

The `z3` one is the worst failure mode the course has, because it is silent:
there is no compile error, there is one loose line in the output —`Tried: $ z3
--in`— and after that every `randomize()` returns 0. `apt install z3` /
`brew install z3`. The Docker image and the devcontainer already bring it.

## Functional coverage: it works, with holes

Covergroups landed in **Verilator 5.050** (2026-07-01) and were extended in
5.052. The *Coverage* column of the matrix is the real number
`verilator_coverage` reports, not a placeholder.

The flow is: compile with `--coverage-user` and call `cov_report` after the run.
The `.dat` ends up in `obj_dir/<top>/coverage.dat`.

```
Coverage Summary:
  covergroup : 86.8% (66/76)
```

What it **does** measure: coverpoints, value and range bins, `ignore_bins`
—with the caveat in the table below—,
implicit cross, and of the covergroup options these two:

| Works | Detail |
|---|---|
| `option.auto_bin_max` | in the covergroup and in the coverpoint. The default is 64 |
| `option.at_least` | **only written in the coverpoint** |

What it does **not** (5.052), and that is why the numbers above are not those of
a commercial tool:

| Missing | What happens |
|---|---|
| transition bins (`=>`, `[* n]`) | Internal Error, does not compile |
| `binsof` / `intersect` / explicit cross bins | `%Warning-COVERIGN`, it ignores them and carries on |
| automatic bins of an `enum` | one per value of the **base type** and not per member: `operation_t` is `bit [2:0]`, and the `3'b110` the enum does not have comes out as `auto_5` and stays at 0 forever. Hence the 86.8 % above: the 10 missing bins are that value and its 9 crosses |
| `option.at_least` in the **covergroup** | it ignores it **without warning**: the coverpoints keep counting with one hit |
| `option.weight` | `%Warning-COVERIGN`, it ignores it and carries on |
| `ignore_bins` | it honours them when filtering, but **emits a bin for each one and counts it as covered**: in `u2/convencional` they are `all_ops.null_ops` (664 hits) and `borrow.resto` (2156). A compliant tool would not report them |
| `type_option.merge_instances` | no observable effect, because type-wide coverage gives 0 anyway |
| `get_coverage()` type-wide | always returns 0 — you have to use `get_inst_coverage()` |
| `$stop` | it aborts before writing the `.dat` — you have to end with `$finish` |

The `at_least` one is the worst in the table because it is silent: the same line
holds in one place and does not in the other, without a warning. A covergroup
asking for ten hits per bin reports as if it asked for one.

The transition bins of the course stayed in the code, between
```ifndef VERILATOR```: they are part of the topic and they read the same.
Minimal repro of the four points: `code/verilator/repro-cg-transition.sv`, and of
the options: `code/verilator/repro-cg-options.sv`, which ends in `$fatal` if any
of the six numbers moves.

## Assertions (SVA): they work, and you have to ask for them

The three SVA examples compile with `--assert` (`u8/assertions`, `ejercicios/d7-sva`
and stage 5 of `ejercicios/d7-final`). **Without
that flag the concurrent properties compile and are not evaluated**: there is no
warning, the run gives 0 errors and the whole block of the interface is
decoration. It is the worst failure mode after the `z3` one, and for the same
reason: it is silent.

```sh
verilator --binary --timing --assert --coverage-user ...
```

Measured on 5.052, with the block in `code/u8/assertions/vtalu_bfm.sv`:

| Works | Detail |
|---|---|
| `assert property` / `cover property` | also **inside an `interface`**, with UVM linked in |
| `\|->` `\|=>` `##n` `##[a:b]` | the `##[1:5]` window of unit 8 |
| `$rose` `$fell` `$stable` `$past(x, n)` | |
| `throughout`, `b[->1]` | |
| named `property` / `sequence` with arguments | **signal** arguments |
| `default clocking`, `default disable iff` | |
| the assertion's `else`, with `` `uvm_error `` | it counts in the **Report Summary**, and `uvm_summary_ok` detects it without touching anything |
| `%m` in the message | it says **which instance** of the interface failed |
| `cover property` in the same `coverage.dat` | it comes out as `user:` next to the `covergroup:` |

| Missing | What happens |
|---|---|
| a `sequence` formal used as a **delay** (`sig ##n !sig`) | `Delay value is not a non-negative elaboration-time constant`, does not compile. With the literal delay it works |

The default action of an assertion without `else` is `$stop`, and in this flow
that is what you do **not** want: it aborts before writing the coverage `.dat`
and before UVM prints the summary. Always `else` with `` `uvm_error ``.

## Clocking blocks: they work, and there is a race that is NOT visible here

The `clocking block` of unit 2 works on 5.052: `default input #1step output #0`,
`@(cb)` as an event, and the sampling of the stable value before the edge.
`code/u2/clocking/` exercises them, and `con_clocking.sv` ends in `$fatal` if the
sampling stops giving the expected value — that is, if a future version changes
the semantics, the CI says so.

What **cannot** be shown with Verilator is the race on the *driving* side.
Measured on 5.052:

```systemverilog
@(posedge clk); d_in  = 8'd10;   // blocking
@(posedge clk); d_in <= 8'd10;   // non-blocking
```

Both give **the same result**. The race with `=` depends on the order in which
the simulator runs the processes of the Active region, and that order is not
defined by the LRM: Verilator picks one and is consistent with itself. On another
simulator it can go the other way.

It is the worst kind of bug there is —it passes on your simulator and fails on
the customer's— and that is why the course tells it but does not demonstrate it:
there is no honest way to demonstrate it with a single tool. The rule holds
anyway: **the driver drives with `<=`**.

What is demonstrated, and is the trap the clocking block adds, is the mixing of
domains: `code/u2/clocking/mezcla.sv` prints `3` and `4` for the same wire at the
same instant, depending on whether you read `bfm.cb.d_out` or `bfm.d_out`. The
full discussion, with the sources, in
[`clocking-blocks.md`](../clocking-blocks.md) (in Spanish).

## RAL: it works whole, and it is the news

The register layer is the part of UVM nobody said whether it worked on Verilator,
so **it was tested before a single slide was written**. Everything unit 9 uses
works. Measured on 5.052, with `code/u9/ral/`:

| Works | Detail |
|---|---|
| `uvm_reg_block` / `uvm_reg` / `uvm_reg_field` | `configure()`, `create_map`, `add_reg`, `lock_model` |
| `uvm_reg_adapter` | including the `const ref uvm_reg_bus_op` of the `reg2bus` signature |
| frontdoor `write()` / `read()` | through the capstone's sequencer and driver, without touching them |
| `mirror(UVM_CHECK)` | it reports the mismatch, and it respects `set_compare(UVM_NO_CHECK)` |
| automatic **and** explicit prediction | `set_auto_predict(0)` + `uvm_reg_predictor` hanging off the monitor |
| `uvm_reg_hw_reset_seq`, `uvm_reg_bit_bash_seq` | both generate stimulus from the model and catch a badly declared access |
| `get_offset`, `get_fields`, `get_access` | the introspection with which `mapa_test` prints the map |

No new flags: the same ones as `vlt_uvm`, plus `-Wno-WIDTHEXPAND`, which only
removes noise — `uvm_reg_data_t` is 64 bits and any 32-bit literal gets widened.

What the course did **not** test, and that is why it is not in the unit: the
**backdoor** (`add_hdl_path` and `uvm_reg_backdoor`), which depends on the
simulator's hierarchical access, and with it the sequences that need it —
`uvm_reg_access_seq` among them.

## The hole that got closed: interface tasks through a virtual interface

**Fixed in Verilator 5.052** (2026-09-05). It stays documented because the course
supports 5.050 onwards, and on 5.050 and 5.051 the problem is present.

Up to 5.051, a task declared **inside an interface** and invoked **through a
virtual interface** wrote the signals, but did not wake up the combinational
logic that depended on them. Verilator did not warn: it compiled clean and
simulated wrong. On the VTALU it looked like this — `op_set` changes, `op` does
not:

```
[t=310] op_set=001  op=000  start=1  start_single=0  done=0
```

With `op` stuck at `no_op`, `done` never went up and the testbench stayed in its
`while (done == 0)` forever. It was the dangerous case: not a compile error, but
a simulation that lies.

Minimal repro: `code/verilator/repro-vif-task.sv`. Measured, three runs,
deterministic:

| | `op_set` | `op` | `y` |
|---|---|---|---|
| Expected (IEEE 1800-2017) | 101 | 101 | 1 |
| Verilator 5.048 | 101 | **000** | **0** |
| **Verilator 5.052** | 101 | **101** | **1** |

While the bug was open, the course moved the protocol (`reset_alu`, `send_op`)
out of the interface and into the class that used it. **With the bug closed it
was moved back**: the protocol lives again in `vtalu_bfm.sv`, which is where unit
3 puts it and where Salemi's book puts it. The driver of an agent ended up three
lines long: ask for the item, `bfm.send_op(...)`, `item_done()`.

The `vcs_base_tester.svh` files were deleted, along with
`u4/reporting/vtalu_tlm_bfm.sv`, `u4/reporting/vtalu_driver_c.svh` and
`u4/tests/tb_classes/selfcheck.svh`. No flow compiled them and no slide showed
them.

## And two more, on the constraints side

They came out of writing the Constrained Random unit. Both compile clean and
simulate wrong, which is the dangerous class.

| Missing | What happens | Repro |
|---|---|---|
| `solve ... before` | it is accepted and NOT respected: it leaves the control field stuck at 0, worse than ignoring it | `code/verilator/repro-solve-before.sv` |
| `randomize() with {}` over a field with a `dist` | the `dist` gets solved by picking a value BEFORE checking the rest: if it does not satisfy it, it returns 0 instead of retrying | `code/verilator/repro-dist-with.sv` |

Both have a portable workaround, and both are in the slides:

- instead of `solve es_reset before A`, ask for the spread of the control field
  with a `dist` — Verilator does respect that one (51.7 % measured against 0.3 %
  with nothing);
- before the directed `with {}`, switch off the spread constraint with
  `constraint_mode(0)`, which for a directed case makes no sense anyway.

The second one does not fail always nor never: it fails **with the probability
that the drawn value does not satisfy the `with`**. With
`A dist {8'h00 :/ 1, [8'h01:8'hFE] :/ 2, 8'hFF :/ 1}`, measured over 400
randomizations:

| `with {}` | success | why |
|---|--:|---|
| `A == 8'hFF` | ~25 % | the weight of the `FF` bin |
| `A inside {[1:10]}` | ~2 % | 10 values out of the 254 of the middle bin, × 50 % |
| `A != 8'h00` | ~75 % | it only fails when it draws the `00` bin |
| `B == 8'hFF` | 100 % | `B` has no `dist` |

A field without a `dist` is not affected. The typical symptom is the worst of
all: **an intermittent directed case**, which works on your machine and fails in
the regression.
Since 5.052 the failure at least **warns**: every `randomize()` that finds no
solution emits a `%Warning-UNSATCONSTR` with the exact constraint that could not
be satisfied. It still returns 0 and the `assert(randomize())` is still needed
—the warning goes to the log, not to the Report Summary— but it is no longer a
completely silent trap.


The same happens with a **class** constraint over a field that has a `dist`,
without a `with {}` in between: `addr dist {...}` next to `addr[1:0] == 2'b00`
comes out with two `%Warning-UNSATCONSTR` and `randomize()` at 0. The way out is
to write the `dist` with the already-good values, one by one, instead of a range
plus a constraint that trims it -- which is what
`code/ejercicios/d7-final/solucion/tb_classes/apb_transaction.svh` does.

What **does** work of constraints: `dist` with `:=` and `:/`, `inside`,
implications (`->`), `constraint_mode()`, `rand_mode()`, and
`randomize() with {}` as long as it does not restrict a field that has a `dist`.

## A trap when editing: a comment that starts with "verilator"

A `//` whose first token is `verilator` **is not a comment**: Verilator reads it
as a pragma and the build dies with `%Error-BADVLTPRAGMA`. Neither the case nor
how many spaces there are in between matters.

```systemverilog
// verilator --binary ... repro.sv     <- breaks the build
// Verilator 5.052 returns 0 ...       <- breaks the build
//   $ verilator --binary ... repro.sv  <- ok, the first token is "$"
// On 5.052 it returns 0 ...           <- ok
```

The three `code/verilator/repro-*.sv` fell into this: the line documenting how to
run them started with `verilator`, so none of the three compiled —including the
one the transition-bins slide quotes—. If you are going to write the command in a
comment, put a `$` prompt in front of it.

## An example "passing" is not enough

PASS means it compiled, ran, exited with code 0 and that UVM's Report Summary
closed at 0 UVM_ERROR / 0 UVM_FATAL — `run_sim` parses it, because UVM does not
change the exit code for a `uvm_error`. The only opt-out is u4/reporting, which
breaks the scoreboard on purpose. The check that gives it weight is u4/tests: it
ends with **0 UVM_ERROR / 0 UVM_FATAL** and with the `$finish` at **41 ns**, the
same point where it ended with UVM 1.2 — which in turn marked `TEST_DONE @
40540`, exactly the number of the reference run kept in
`code/u4/tests/output.questa`.

That `TEST_DONE` no longer shows up: in IEEE 1800.2 the objection does not emit
that UVM_INFO. The comparison chain is still closed anyway (Questa 1.1d ->
Verilator + UVM 1.2 -> Verilator + UVM 2020.3.1), but the anchor is now the
`$finish` time, not the message. `output.questa` stays as a witness, not as a
flow.
